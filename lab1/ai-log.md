## Запис AI-02 — Контракт даних і комплектність

- Лабораторна: ЛР01; дата: 10.10.2026.
- Відповідальний за перевірку: Кириченко.
- Інструмент / режим / модель: Codex / аналіз вимог і перевірка специфікації / GPT-6 Astra.
- Мета: Контракт даних і комплектність.
- Контекст: Два типи послуги; правила назви, опису, enum, авторів і PATCH.

**Повний ключовий запит підзадачі:**

> Формалізуй Request, CertificateDetails, CorrectionDetails, Comment, Resolution та AIRecommendation. Для кожного поля визнач тип, джерело, required, default, null, нормалізацію, межі та редагування. Неповні реквізити дозволяй в OPEN, невалідні значення відхиляй. Підтвердження типу зроби явним без додавання авторизації. Уточни структуру реквізитів результату окремо для довідки та виправлення даних.

**Аналіз прийнятого та відхиленого:** Прийнято: confirmation pair, серверний UTC, nullable неповні деталі, типізований result_details; за повторною перевіркою явно додано ШІ-перевірку комплектності у ЛР4 та AC-08-04. Уточнено: довільне текстове result_details не забезпечує перевірюваних реквізитів за типом послуги; використано об’єкт. Відхилено неструктурований результат як остаточний контракт.

**Перевірка:** Звірено обов’язкові поля послуг із погодженим описом предметної області; додаткові довжини та формат результату позначено D-08, а не заданими вимогами.

**Артефакт:** requirements.md §6; api-contract.md §1.

## Запис AI-03 — Стани, PATCH і критерії

- Лабораторна: ЛР01; дата: 10.10.2026.
- Відповідальний за перевірку: Кириченко.
- Інструмент / режим / модель: Codex / аналіз вимог і перевірка специфікації / GPT-6 Astra.
- Мета: Стани, PATCH і критерії.
- Контекст: Матриця трьох статусів; атомарність; відсутність поля проти null; OPEN → CLOSED.

**Повний ключовий запит підзадачі:**

> Побудуй всі дев’ять комбінацій статусів OPEN, IN_PROGRESS і CLOSED. Перехід до IN_PROGRESS дозволяй лише після підтвердження й комплектності. Для CLOSED вимагай результат або мотивовану відмову, збережи ідемпотентний повтор поточного статусу. Опиши шість граничних випадків PATCH, вкладений merge і атомарність. Сформуй User Stories з позитивними, граничними та негативними Given-When-Then.

**Аналіз прийнятого та відхиленого:** Прийнято: 9 переходів, no-op для однакового статусу, резолюція в одній транзакції зі статусом. Уточнено: повтор CLOSED без resolution дозволений, але змінити стару resolution не можна; IN_PROGRESS не може втратити комплектність. Відхилено редагування CLOSED і автоматичне перенесення тексту коментаря в реквізити.

**Перевірка:** Перераховано 3×3 комбінації; звірено 400/404/409/422; усі AC-01..AC-07 включено в CSV.

**Артефакт:** requirements.md §5, §7–9; traceability.csv.

## Запис AI-05 — API і машиночитані схеми

- Лабораторна: ЛР01; дата: 10.10.2026.
- Відповідальний за перевірку: Корякін.

- Мета: API і машиночитані схеми.
- Контекст: Десять заданих маршрутів; усі моделі й матриця; каталог помилок.

**Повний ключовий запит підзадачі:**

> Підготуй усі десять заданих маршрутів REST API з path/query, JSON Schema body, повним успішним прикладом і релевантними 400/404/409/422. Для GET визнач відсутність тіла. Не створюй альтернативних бізнес-правил: посилайся на requirements.md. Додай повні локальні JSON Schema definitions і звір приклади. Обидва маршрути закриття мають викликати один доменний сценарій.

**Аналіз прийнятого та відхиленого:** Прийнято: Error envelope, AND-фільтри, strict вхід, complete schemas, два входи одного close_request. Уточнено: schema статусу не може вимагати resolution для будь-якого status=CLOSED, бо повтор CLOSED має бути 200 без неї; цю залежність перевіряє service. Відхилено універсальне required для resolution у StatusPatch.

**Перевірка:** Validator перевірив JSON-схеми, усі 33 збережені приклади та локальні посилання; 10 негативних прикладів відхилено (набір попередньої редакції контракту, склад не зафіксовано; актуальну перевірку див. «Повторна перевірка прикладів API»). Результат повторної перевірки зафіксовано в lab-01.md §5.

**Артефакт:** api-contract.md §1–2.

## Повторна перевірка прикладів API

Дата: 20.10.2026. Інструмент: Claude Code. Модель: Claude Opus 5.5. Відповідальний за перевірку: Корякін.

Причина: зауваження рецензента — у звіті вказано 33 приклади та 10 негативних входів, тоді як поточний api-contract.md містить 40 JSON-прикладів, а склад перевіреного набору не зафіксовано.

Перевірка: виокремлено 104 JSON-блоки контракту — 64 блоки схем і 40 прикладів (7 тіл запитів, 10 успішних відповідей, 23 тіла помилок). Кожний приклад провалідовано за відповідною схемою (JSON Schema Draft 2020-12, definitions §1). Сформовано 12 негативних входів N-01..N-12 зміною одного поля валідних прикладів запитів відповідно до AC-01-03, AC-03-02..AC-03-04, AC-04-05, AC-05-03, AC-06-02, AC-06-04, маршрутів 2.7/2.8 і FR-07.

Схеми Request, Completeness і StaffList посилено інваріантами однієї відповіді за зауваженням рецензента; сформовано 11 недопустимих відповідей R-01..R-11 і 4 допустимі граничні стани A-01..A-04. Перевірки, які схема не виражає, перелічено в api-contract.md §6.

Результат: 24 схеми коректні; 40 із 40 прикладів валідні; 12 із 12 негативних входів і 11 із 11 недопустимих відповідей відхилено; 4 із 4 допустимих станів прийнято. Склад набору зафіксовано в api-contract.md §5; lab-01.md §4.1 і §5 оновлено.
