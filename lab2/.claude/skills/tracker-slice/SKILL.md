# Реалізація одного зрізу «Сервісу студентських звернень»

Специфікація ЛР1 у docs/ — єдине джерело правил. Не змінюй її, щоб спростити патч.
Бізнес-правила — docs/requirements.md; маршрути, схеми й приклади — docs/api-contract.md.
Шляхи docs/, app/, tests/ — від кореня репозиторію (теки lab2/); references/ — від теки цього Skill.

## Розподіл відповідальності (docs/architecture.md §1)
- schemas.py — форма входу: strict типи, trim, межі, enum, заборона зайвих полів;
- models.py — value objects реквізитів, результату й комплектності;
- service.py — бізнес-правила: підтвердження типу, merge, комплектність,
  матриця переходів 3×3, закриття, фільтрація;
- repository.py — параметризовані SQL-запити; database.py — схема, з'єднання, транзакції;
- api.py — маршрути й перетворення результатів і помилок на HTTP-відповіді;
- main.py — create_app(db_path, clock).
Розміщуй кожну зміну в шарі, якому вона належить.

## Процедура
1. Визнач зріз (A–E) за запитом. Якщо запит охоплює кілька зрізів, запропонуй
   розділити роботу й почни з одного.
2. Знайди зріз у references/slices.md і прочитай лише зазначені там розділи docs/.
3. Перелічи перевірки: AC і сценарії T-xx, яких стосується зміна.
4. Дай план із 3–5 пунктів і дочекайся підтвердження.
5. Внеси мінімальну зміну лише в дозволених для зрізу файлах, разом із тестами
   для перевірок із кроку 3. Назви тестів бери з docs/traceability.csv.
6. Перед запуском перевір свій diff: якщо він працює з файлами поза tmp_path,
   з мережею, запускає процеси або видаляє дані — зупинись і дочекайся підтвердження.
7. Запусти перевірки з кореня репозиторію:
   python -m pytest -q
   python -m ruff check app tests --select E4,E7,E9,F,I
   Якщо щось падає — виправ код і запусти знову. Після двох невдалих спроб
   зупинись і опиши ймовірну причину: далі діагностує людина.
8. Наведи фактичний підсумок перевірок і окремо — що не зроблено або потребує
   рішення людини.

## Заборони
- Не змінюй маршрути, поля, коди відповідей і коди помилок із docs/api-contract.md.
- Не додавай і не оновлюй залежності; не змінюй налаштування середовища.
- Запускай лише команди перевірки з кроку 7.
- Наявні тести змінюй, лише якщо вони суперечать контракту, і поясни чому;
  не видаляй перевірки й не пропускай тести, щоб вони пройшли.
- Не додавай функцій поза обсягом ЛР1 (requirements.md §1, Out-of-Scope):
  реєстрації, паролів, JWT, OAuth, ролей, email, вкладень, видалення звернень,
  створення співробітників, пагінації, повнотекстового пошуку, GUI, Docker, хмари.
- SQL — лише параметризовані запити; тести — лише на тимчасовій базі (tmp_path),
  ніколи на data/student_requests.sqlite3.
- Невдала команда не змінює БД: перевірка всього кандидата до запису, одна транзакція.
- Не стверджуй, що перевірки пройшли, не запустивши їх. Рішення прийняти зміну —
  за людиною.

## Формат відповіді
Зріз → прочитані розділи docs/ → перевірки → план → diff → підсумок pytest і ruff →
що не зроблено.
